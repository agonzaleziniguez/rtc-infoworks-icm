# From a control objective to an RTC implementation

This guide describes the intended assistant workflow. Server tools are not yet
implemented; the current MCP package is a placeholder.

## Understand before constructing

The user describes an objective in modelling terms. They do not need to choose
Ranges, Tables, Variables, Controllers, or Rules.

For example:

> Depending on the water level at N1, control variable-crest weir W1 so the
> level at N2 does not exceed 10 m.

This is not yet an implementable control specification. The assistant must
understand how N1 relates to the N2 objective, which measurements are available,
the permitted crest levels, and the desired response before choosing a strategy.
The example does not imply that a table or a controller will achieve the goal.

Ask immediately when a missing detail affects the intended behaviour. Ask as
many follow-up questions as needed, including questions discovered during
construction. Do not invent thresholds, network relationships, tuning values,
units, or operating limits. An unavailable capability must be explained, not
silently replaced with a different strategy.

Explain the proposed behaviour in modelling terms and obtain the user's
agreement before constructing it. The user retains authority over the objective
and operational decisions.

## Responsibilities

- **Assistant:** clarify the problem, propose and explain the strategy, and
  select explicit supported library operations.
- **Server:** provide guidance, retain the working definition, translate
  requests into library calls, and return useful validation feedback.
- **Library:** validate fields, references, scope, ordering, and completeness;
  generate properly formatted RTC text.
- **User and ICM:** verify the network, imported settings, and hydraulic results.

There is no second AI inside the server. Server guidance supports the assistant;
it cannot force every assistant host to follow the conversational policy.

## Working control definition

The planned working definition is an ordered list of precise library operations
with arguments and explicit reference IDs. It is not an RTC file or executable
Python source. References identify returned objects, not guessed name matches.

The assistant will be able to insert, replace, or remove identified operations.
The server will build a candidate through the library before accepting a group
of changes. An invalid change leaves the previous definition intact. No
automatic reordering, repair, or deletion of dependent operations is permitted.

Incomplete definitions may exist while work is in progress, but previews and
outputs require complete validity. Keeping a definition in memory supports
iteration; it is not persistent storage or automatic restart recovery.

## Review and outputs

Review the intended behaviour and the constructed result with the user. Ask
whether they want a Python script, an RTC file, or both, and obtain an explicit
saving request.

Both outputs will come from the same working definition. RTC text is always
generated by the library, never edited directly. A generated Python script will
contain equivalent library calls; the server will not execute supplied scripts.
Saving does not close the working definition or prevent further edits.

The planned export service will save only in a configured directory and require
explicit permission to overwrite existing files.

## What validation establishes

Keep three questions separate:

1. Does the proposed behaviour match the user's objective? Clarification and
   review establish this.
2. Does the RTC document correctly express the supported implementation?
   Library validation and construction tests establish this.
3. Does the strategy achieve the objective in the actual model? ICM testing
   establishes this.

Never present successful RTC generation as a guarantee of hydraulic performance.
